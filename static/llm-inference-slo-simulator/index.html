Get a feel for TTFT, ITL, and request-latency SLOs

Pick a workload, then drag traffic load past 100% of estimated engine capacity and watch tail latency stop being flat. The simulator runs a small discrete-event model of a continuous-batching scheduler — decode tokens are served first every iteration, chunked prefill spends whatever token budget is left over, same as a real vLLM-style engine — over a batch of synthetic requests, then reports p50/p90/p95/p99.

Throughput numbers per GPU/model tier are illustrative round numbers for building intuition about queueing and batching interference, not calibrated hardware benchmarks. Use it to feel the shape of the problem, not to size a cluster.

Model: each iteration, currently-decoding sequences each consume one token of the iteration's token budget; whatever budget remains is spent chunk-prefilling admitted requests in FCFS order, capped at 256 tokens per request per iteration so one long prompt can't monopolize a step (the same reason real engines cap chunked-prefill size). The iteration's wall-clock length is a fixed per-step floor (weight-read / launch overhead — why decode is memory-bandwidth bound and roughly batch-size independent) plus tokens_processed ÷ compute throughput for whatever that step processed. TTFT is measured from when a generation call is issued (after retrieval, for RAG) to its first produced token. ITL is the gap between consecutive decode tokens for a sequence — it widens whenever a chunked prefill shares an iteration with active decodes. Request latency is end-to-end, including any queueing for an admission slot, retrieval, and (for agents) tool round-trips between steps.
